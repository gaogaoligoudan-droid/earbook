# EarBook 需求 vs 业界方案对照报告（R1-R11 外部校准）

> 2026-10-07 · 码龙 · 范围：开源听书生态（Legado 系/KOReader/tts-server-android）、
> 学术管线（Calliope）、成熟商业 App（Moon+/@Voice）、Android 官方约束
> 用途：借鉴 + 避雷 + 印证，**不改需求，只校准实现细节**

## 二、直接借鉴（3 条进实现细节）

1. **双层缓存结构**（legado-tts 修复模式）：句级 PCM 留内存 LRU（播完即释）+ 章级
   AAC 落盘（一次原子写）——我们的 ChapterAudioCache 已是章级落盘 ✓，M1 加「句级
   内存预取层」即完整复刻该模式
2. **可靠性模式**（tts-server-android）：自动重试+备用配置——R7 已拍板「失败不重试」，
   但**引擎层**（非 API 层）的备用可借鉴：神经引擎初始化失败 → 自动落系统 TTS 并提示
   （与 R6 弹窗策略兼容，实现时一并设计）
3. **前台服务类型声明**：`mediaPlayback`（播）+ `dataSync` 或短服务（渲）双类型，
   Android 17 合规——M2 调度层实现时带上

## 三、避雷清单（2 条硬雷）

1. **段落级磁盘缓存**（Legado 系实锤翻车）：任何「每句/每段一写一删」的设计禁止——
   章级原子写是底线粒度
2. **CJK 文本结构破坏**（Calliope 教训）：AI 优化层必须保结构——章节标题/段落边界/
   对话引号不可被 LLM 改写丢失，否则分章和断句全乱（R7 的 prompt 工程硬约束）

## 四、意外发现（v2 候选，仅记录不入档）

**tts-server-android 的反向思路**：把我们的本地神经引擎**注册为 Android 系统 TTS
服务**——Legado/Moon+ 等所有阅读 App 即可直接用 kokoro 神经声朗读，EarBook 变成
「全系统语音供给方」。这改变了产品定位（从听书 App → 语音基础设施），值得 v2 议题。
另有：对话双音色（中文双引号旁白/对话识别，tts-server-android 已实现——旧 roadmap
M4 里我们本来就规划过）、句级高亮同步（KOReader 模式）。

## 五、结论

**需求体系无一条与业界实践冲突；两条硬雷已有具体规避；三个实现细节直接吸收。**
R7（LLM 文本优化）是唯一无成熟产品先例的差异化点——有学术同向（Calliope），
风险在 prompt 工程保结构，已列入 M1 实现约束。
